Phase 3 — Wallets: CDP out, Hedera accounts in\n\n### 6.0 Custody model — this build is CUSTODIAL, and why\n\nTo remove any ambiguity: **the platform holds every user's Hedera private key.** Keys are generated server-side, sealed with GCP KMS, and unsealed only inside `\"use server\"` code paths to sign a payment. There is no browser wallet, no HashPack, no WalletConnect, no user-held seed phrase anywhere in this build.\n\nThis is a deliberate choice for this build. The reasons, accurately:\n\n- **Purchases already sign server-side.** The existing flow runs through server actions, so custodial signing is a provider swap (Coinbase CDP → Hedera + KMS), not a new trust model. Going non-custodial means moving the payment leg into the browser and rewriting `actions/actions.ts`, the 402 retry loop, and the buy UI.\n- **It preserves email/password onboarding.** A user signs up and can buy immediately. Non-custodial requires them to install a wallet and acquire testnet HBAR before the product does anything, which is a materially worse first run.\n- **It keeps the browser test suite honest.** Because signing happens in a server action, a Playwright click on \"Buy\" performs a _real_ payment with nothing to mock (§11.5). With a browser wallet you would be driving an extension in headless Chromium or stubbing the signer, and the suite would stop exercising the real payment path.\n\n**What is _not_ a reason:** autonomous agent purchases. `mcp.mjs` is a **stdio** MCP server — it runs on the user's own machine, so its key can live in that machine's environment and never touch the platform (§10). Agent autonomy does not require platform custody, and the plan does not claim otherwise.\n\n**The tradeoff, stated plainly:** the platform is a custodian. A compromise of the KMS key or the database puts user funds at risk, and on **mainnet** custody of third-party funds raises real regulatory questions (money-transmission / VASP-style obligations, depending on jurisdiction) — out of scope for a testnet build with valueless HBAR. In-scope mitigations: KMS envelope encryption (D6), `select: false` on the key field, plaintext keys never logged or returned by any API, and the `PaymentSigner` seam in §7.0 so this decision is reversible.\n\n**The non-custodial path exists and is deliberately deferred, not ruled out.** Hedera has the primitives: `hedera_signTransaction` / `hedera_signTransactions` (HIP-820, HIP-1190) return signature maps only, which is exactly the x402 fee-payer model where the facilitator co-signs and submits; and HIP-336 `AccountAllowanceApproveTransaction` grants a capped, revocable spending allowance to a platform spender account without the platform ever holding a key. **Do not build either now.** They are noted so a future engineer knows the door was left open on purpose.\n\n### 6.1 New modules\n\n**`app/lib/hedera/client.ts`** — singleton `Client.forTestnet().setOperator(config.hedera.operatorId, config.hedera.operatorKey)`; export it plus a `treasuryClient` variant using the treasury key.
